# 0022 黑绿线 P40–P45 只在稳定趋势里、只照着色插件的颜色判；交易计划暂不变

- 状态：采纳
- 日期：2026-11-21

## 背景
`rules.md` 的 P40–P45 是 LEI 黑绿线指标的用法（视频 P、M）：多头排列里绿做多、变黑平仓，空头排列里黑不做多、变绿不做多，灰色是警报不动手，上升趋势里一直是绿就不用关心。LEI 没有公开指标代码，这几条一直是需看图。

0020 之后，本机可以配一个着色插件，给 K 线一套更接近的私有颜色。仓库自带的着色只看 MA20 的破线和拐头，不是黑绿线。用户批准把这几条接进计算，先在核心名单上回测，看它们对交易结果是好是坏，再决定接不接进交易计划。

## 决定
适用范围是硬条件：只在类型是稳定上涨、稳定下跌时判。横盘、加速上涨、加速下跌和过渡状态（J6）一律不满足，依据写"黑绿线不适合<类型>"和视频 P 的出处。

只认着色插件的颜色。没配插件、插件出错退回自带着色时，这几条仍是需看图，不是不满足。依据里写明用的是哪套颜色。

判法：MA20 > MA60 且 EMA20 > EMA60 是多头排列，两个都小于是空头排列，不一致时 P40–P43 不满足。颜色看今天这根。六条按颜色互斥，结论不打架，没有让位。

交易计划暂不变。`tradeplan.py` 的进场、止损、目标、盈亏比不读黑绿线。分析 JSON 多一个 `bwl` 读数，结论卡片多一行"黑绿线（来源名）：一句话"，只在配了插件、类型适用时出现。

`dma_analyze.analyze()` 默认不读插件，只有命令行（不带 `--builtin-tones`）和完整计划回测读。识别题的 `scan.py`、练习的分析在每台机器上一样。

回测开关默认关。`fullplan.py` 每天记下哪几条黑绿线成立。`--bwl-exit`：持仓时 P41 或 P42 收盘成立，按失效条件次日开盘离场；`--bwl-entry`：只下 P40 成立那天的单。两个都关时，单和成交和不看黑绿线逐笔相同。回测结果只在本机，不进仓库。

## 理由和出处
- 用户决定（2026-11-21）：先接进计算、先回测，接不接进计划看了回测再定。
- 视频 P 01:25「这个指标的缺陷就是不适合在三点钟方向的」：横盘里反复变色。
- 视频 P 01:42「这种快速反转 它是来不及反应的」：12 点、6 点钟方向的加速。
- 视频 P 01:59「这个指标最适合的趋势方向 其实是两点钟方向的上涨趋势」：后半句是四点钟方向的下跌趋势。
- 自带着色只取了黑绿线三个因子里的第一个（视频 P 00:41「黑绿变色的逻辑结合了三个主要的因素」），拿它判这几条会把破线拐头当成黑绿线。
- 交易计划不变，回测开关默认关：没看到回测结果之前，不让新规则改变已有的数字和卡片上的价位。

## 影响
- `rules.py` 的 `read_bwl` 读一次颜色和排列，P40–P45 各有一个函数（`rules.md` 的"由哪个计算判断"）。`Ctx` 多两个字段：`tones` 和 `tone_source`。
- 改了 0020 的两处：规则读颜色了（只有 P40–P45）；`tones.py` 进完整计划缓存的指纹，指纹还带上插件文件内容的哈希（只算哈希，不输出内容），换了插件或去掉插件就重算。
- 依据、卡片和分析 JSON 里会出现插件的名字，只在本机。网页报告（`--html`）不写规则清单和 `bwl`，仍不带插件的东西。
- 完整计划每天的计划里多一次着色插件的调用，计划计算会慢一些。
- 工作台的回测页（`planrun.py`）用同一份每天的计划缓存，配了插件后会重算一次。

## 什么情况下重新考虑
核心名单的回测看完、用户决定接不接进交易计划时，补一条决定（已补：0024，不接）。LEI 公开了黑绿线的代码或完整规则：照他的写，自带着色也能判。插件换成一套和黑绿线差得远的规则：这几条该回到需看图。
